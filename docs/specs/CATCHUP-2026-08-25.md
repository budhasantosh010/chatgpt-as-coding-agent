## 1. What this project is, in four lines

A local MCP server that lets a **normal ChatGPT subscription** write code on the
operator's Windows machine. ChatGPT is the brain; this repo is the hands.

**No model-provider API is ever called.** Not OpenAI, not Anthropic, not a local
LLM. The entire point is £0 beyond the ChatGPT subscription already paid for. If
a task looks like it needs a model, the answer is *"ChatGPT does that part."*

## 2. What changed most recently (this is the new part)

### The second door — ngrok alongside Tailscale

ChatGPT reaches the machine through a tunnel. There is now a **second** tunnel,
because some networks block Tailscale on purpose and nothing on the operator's
side fixes that.

```
                       ChatGPT
          +---------------+---------------+
          v                               v
   Tailscale Funnel                     ngrok            <- TWO ROADS
          +---------------+---------------+
                          v
                   localhost:8848                        <- ONE ENGINE
        tasks · workspaces · evidence · git · files      <- ONE SET OF STUFF
```

**Not two harnesses — two entrances to one building.** Nothing syncs or
migrates. It is flown and working: on 2026-08-25 ChatGPT created and read back a
real file on the machine through the ngrok path.

**Before you touch host handling, the tunnel scripts, or the `.bat` launchers,
read [second-door-decision-log.md](second-door-decision-log.md).** Several
choices in there look like inconsistencies worth tidying and are not:

| Looks wrong | Why it is deliberate |
|---|---|
| ngrok host is exact-match, while `.ts.net` uses a wildcard | `*.ts.net` is the operator's own tailnet. `*.ngrok-free.dev` is shared with every other ngrok customer. |
| `start-ngrok.bat` refuses to call Tailscale | It exists for networks where Tailscale is dead. Calling it would defeat the file. |
| `check-ngrok.ps1` omits the header that would make it pass | ChatGPT does not send that header either. A check that papers over the failure it detects is worthless. |
| `HARNESS_PUBLIC_HOST` duplicates `HARNESS_ALLOWED_HOSTS` | It does not. `ALLOWED_HOSTS` **replaces** the default list; naming a tunnel there 403s the operator's own Workbench. |

### The dependency pin

`mcp` was declared `>=1.26` with no upper bound. **mcp 2.0 removed
`mcp.server.fastmcp`**, which `harness/server.py` imports. A clean install
resolved to 2.x and died at import — which is why CI was red from 2026-07-28
onward while the laptop stayed green on a stale 1.26.0.

Now pinned `mcp>=1.26,<2`. **That bound is load-bearing.** Lifting it means
porting `server.py` to the 2.x API first. Verified by bisect: `fastmcp` exists
through 1.29.1, gone in 2.1.0.

## 4. THE ONE OPEN ITEM — three CI failures that pass locally

All three pass on the operator's Windows laptop. All three fail on GitHub
Actions. They were invisible until the `mcp` pin let CI get past import for the
first time since July.

### 4a. `tests/test_observations.py` — two failures, ubuntu only

```python
# tests/test_observations.py, test_write_batch_records_...
{"path": r"new\file.txt", "content": "new\n"},      # <- a WINDOWS path
...
assert [e["path"] for e in events] == ["tracked.txt", "new/file.txt"]
```

```
   On Windows:  r"new\file.txt"  is a directory + a file.
                Normalization turns it into "new/file.txt".   PASSES

   On Linux:    r"new\file.txt"  is ONE filename that happens to contain a
                backslash. There is nothing to normalize, so it stays
                "new\file.txt".                               FAILS
```

CI's actual output confirms it: `assert ['tracked.txt...ew\\file.txt'] ==
['tracked.txt...new/file.txt']`. The sibling test fails with `IndexError: list
index out of range` for the same root cause — the expected events were not
produced.

**Assessment: the TEST is wrong, not the code.** It hardcodes a Windows path
convention and asserts it cross-platform. Likely fix: build the path with
`os.path.join` / `Path`, or mark the backslash-normalization case
`@pytest.mark.skipif(os.name != "nt")`. **Decide which the behaviour actually
is** — if the harness is *supposed* to normalize backslashes everywhere, the
code needs the fix instead. That question is not yet settled.

### 4b. `tests/test_executor.py::test_local_executor_runs_command` — windows CI only

```python
ex = LocalExecutor("")                                   # "" = auto-detect shell
result = run(ex.run("echo harness_ok", tmp_path, timeout=30))
assert result.returncode == 0     # CI gets -1
```

Passes on the operator's Windows machine, fails on `windows-latest`. A
returncode of `-1` usually means the process never spawned or was killed, not
that the command errored. Hypotheses, untested:

- shell auto-detect (`""`) resolves differently on the runner image
- PowerShell execution policy or startup profile on the runner
- the 30s timeout being hit on a cold runner

**Do not guess-fix this.** Reproduce it first — and note that reproducing means
a CI run, which costs minutes the operator does not have until **1 September**.

### How to work on these without spending CI minutes

The failures are platform-specific, so a local Windows run cannot see the ubuntu
ones. Options, cheapest first:

```
 1. Reason from the CI logs already captured above (free).
 2. WSL / a Linux container locally for the ubuntu failures (free).
 3. Wait for 2026-09-01 and iterate on CI (costs minutes).
```

## 5. How to run it

```bash
python -m pip install -e ".[dev]"
python -m harness doctor          # config + environment; run this first
python -m pytest tests -q         # 484, ~95s on Windows
```

What the operator double-clicks:

```
start-harness.bat   tailscale -> funnel -> engine(:8848 + :8849) -> verify
stop-harness.bat    funnel down, then kill whatever listens on 8848/8849
start-ngrok.bat     STANDALONE ngrok path; starts the engine itself, never
                    calls Tailscale. Run both launchers for two doors at once.
```

There is **no `harness down`** — that is why `stop-harness.bat` stops by port.

Repeatedly, a green signal missed something a single real attempt caught:

```
   2026-07-24  the fork bug           green suite, broken in flight
   2026-07-28  F1 / F2                green suite, broken in flight
   2026-07-29  F3                     green suite, broken in flight
   2026-08-25  ngrok floor + Defender green suite, blocked outside the process
   2026-08-25  mcp 2.0 unpinned       green LAPTOP, red CI, for a month
   2026-08-31  engine window closed   "status: on" everywhere, 502 in flight
```

**A green signal proves whatever it actually measured, which is never quite the
thing you assumed.** After any change to how the outside world reaches this
harness — fly it. After any dependency change — install clean and run the suite,
because your machine and CI are otherwise running different programs.

And the rule that governs the writing here: record the **decision and the
alternative rejected**, not just the outcome. A conclusion alone is worthless in
six months.
